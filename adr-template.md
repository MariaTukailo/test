# Протокол архитектурных решений (ADR) для проекта «Evently»

В данном документе зафиксированы ключевые архитектурные решения, принятые на этапе проектирования веб-приложения «Evently». Документ предназначен для фиксации обоснований выбора технологий.

---

## ADR-001: Выбор реляционной СУБД PostgreSQL для хранения данных

### Метаданные
* **Дата:** 2026-11-02
* **Статус:** Принято (Accepted)
* **Лица, принимающие решения:** Исполнитель (Тукайло М.А.), Заказчик (Огородник Е.В.)
* **Консультант:** Преподаватель (Куприянова Д.В.)

### Контекст и постановка задачи
Веб-приложение «Evently» предназначено для планирования мероприятий. Система должна хранить данные о пользователях, комнатах, чек-листах задач, бюджетах и виш-листах. Все эти данные тесно связаны между собой (например, задача принадлежит конкретному мероприятию, а гость привязан к событию). 
Основной вопрос: какую систему управления базами данных (СУБД) выбрать для обеспечения надежного хранения связанных данных?

### Драйверы решения
1. **Целостность данных:** Требуется поддержка транзакций (ACID) и строгих связей между таблицами.
2. **Стек технологий:** Бэкенд на Java (Spring Boot) требует зрелой интеграции со Spring Data JPA (Hibernate).
3. **Бюджет:** Использование только Open Source решений.

### Рассмотренные варианты
* PostgreSQL
* MySQL
* MongoDB (NoSQL)

### Итог решения
Выбранный вариант: **«PostgreSQL»**, потому что он наилучшим образом удовлетворяет критерию целостности данных (строгая типизация и поддержка связей) и имеет отличную совместимость со Spring Boot.

### Последствия
* **Хорошо, потому что** обеспечивает надежное хранение связанных данных и поддерживает ACID-транзакции. Это критически важно для учета бюджета и синхронизации списка гостей.
* **Хорошо, потому что** существует огромное количество документации и готовых решений для интеграции с Spring Boot.
* **Плохо, потому что** требует более сложной настройки при развертывании в Docker по сравнению с SQLite, однако для production-среды это оправдано.

### Подтверждение
Соблюдение данного решения будет подтверждено на этапе код-ревью (наличие зависимостей `spring-boot-starter-data-jpa` и драйвера `postgresql` в файле `pom.xml`). Также будет проведена проверка схемы базы данных (наличие первичных и внешних ключей).

### Плюсы и минусы вариантов

#### PostgreSQL
* **Хорошо, потому что** поддерживает строгую типизацию и сложные реляционные связи (One-to-Many, Many-to-Many).
* **Хорошо, потому что** имеет отличную поддержку транзакций (ACID), что критично для учета бюджета.
* **Нейтрально, потому что** для базовых запросов требуется знание SQL, но Hibernate скрывает большую часть сложности.
* **Плохо, потому что** занимает больше памяти и ресурсов сервера, чем SQLite.

#### MySQL
* **Хорошо, потому что** очень быстрая для простых операций чтения.
* **Хорошо, потому что** имеет широкую поддержку в веб-хостингах.
* **Плохо, потому что** в некоторых аспектах (например, работа с JSON или сложные аналитические запросы) уступает PostgreSQL.
* **Плохо, потому что** исторически имеет некоторые особенности с поддержкой строгих стандартов SQL.

#### MongoDB (NoSQL)
* **Хорошо, потому что** позволяет гибко менять структуру данных без миграций.
* **Плохо, потому что** не гарантирует строгую целостность данных по умолчанию (отсутствие классических JOIN'ов), что усложняет работу с бюджетами и списками гостей.
* **Плохо, потому что** для сложных связанных данных потребуется дублирование информации, что приведет к аномалиям при обновлении.

### Дополнительная информация
Решение было согласовано на этапе проектирования архитектуры. В случае, если в будущем потребуется экстремально высокая горизонтальная масштабируемость (шардирование), решение может быть пересмотрено в пользу NoSQL. Связанные требования из SRS: REQ-FUNC-001, REQ-FUNC-004.

## ADR-002: Выбор фреймворка Spring Boot для серверной части

### Метаданные
* **Дата:** 2026-11-02
* **Статус:** Принято (Accepted)
* **Лица, принимающие решения:** Исполнитель (Тукайло М.А.), Заказчик (Огородник Е.В.)
* **Консультант:** Преподаватель (Куприянова Д.В.)

### Контекст и постановка задачи
Приложению необходима серверная часть (Backend), которая будет обрабатывать HTTP-запросы, выполнять бизнес-логику (создание мероприятий, управление задачами, расчет бюджета) и взаимодействовать с базой данных PostgreSQL.
Основной вопрос: на каком языке и с использованием какого фреймворка реализовать серверную часть, чтобы обеспечить безопасность и скорость разработки?

### Драйверы решения
1. **Безопасность:** Приложение работает с персональными данными. Требуется встроенная защита (Spring Security).
2. **Интеграция с БД:** Простая работа с PostgreSQL через JPA.
3. **Опыт команды:** Исполнитель знаком с языком Java.

### Рассмотренные варианты
* Java + Spring Boot
* Node.js + Express
* Python + Django

### Итог решения
Выбранный вариант: **«Java + Spring Boot»**, потому что фреймворк предоставляет комплексные встроенные модули для обеспечения безопасности, работы с базой данных и обработки веб-запросов.

### Последствия
* **Хорошо, потому что** строгая типизация Java снижает количество ошибок, а Spring Security обеспечивает надежную защиту.
* **Хорошо, потому что** наличие большого количества документации упрощает поддержку.
* **Плохо, потому что** Spring Boot потребляет больше оперативной памяти при запуске по сравнению с Node.js, что может незначительно увеличить требования к серверу.

### Подтверждение
Проверка наличия зависимостей `spring-boot-starter-web` и `spring-boot-starter-security` в файле `pom.xml`. Код-ревью контроллеров на предмет использования аннотаций `@RestController`.

### Плюсы и минусы вариантов

#### Java + Spring Boot
* **Хорошо, потому что** имеет встроенные модули безопасности и работы с БД.
* **Хорошо, потому что** строгая типизация и огромное сообщество разработчиков.
* **Нейтрально, потому что** требует больше времени на начальную настройку проекта.
* **Плохо, потому что** потребляет больше оперативной памяти.

#### Node.js + Express
* **Хорошо, потому что** очень быстрый запуск и низкое потребление памяти.
* **Хорошо, потому что** можно писать код на одном языке (JavaScript) и на фронтенде, и на бэкенде.
* **Плохо, потому что** отсутствие строгой типизации приводит к ошибкам в рантайме.
* **Плохо, потому что** безопасность и валидация данных требуют подключения множества сторонних библиотек.

#### Python + Django
* **Хорошо, потому что** обеспечивает быструю разработку (встроенная админ-панель).
* **Хорошо, потому что** простой и читаемый синтаксис.
* **Плохо, потому что** работает медленнее, чем Java, при высоких нагрузках.
* **Плохо, потому что** асинхронность реализована сложнее, чем в Spring Boot.

### Дополнительная информация
Решение принято с учетом того, что в команде есть опыт работы с Java. Это позволит избежать затрат на обучение и снизить риски ошибок в коде. Связанные требования из SRS: REQ-SEC-002, REQ-INT-013.

## ADR-003: Выбор библиотеки React для клиентской части

### Метаданные
* **Дата:** 2026-11-02
* **Статус:** Принято (Accepted)
* **Лица, принимающие решения:** Исполнитель (Тукайло М.А.), Заказчик (Огородник Е.В.)
* **Консультант:** Преподаватель (Куприянова Д.В.)

### Контекст и постановка задачи
Необходимо создать быстрый и интерактивный интерфейс для планирования мероприятий, который будет обновляться без перезагрузки страницы (например, при работе с чек-листом).
Основной вопрос: какую библиотеку выбрать для разработки Frontend?

### Драйверы решения
1. **Скорость работы:** Высокая производительность рендеринга (Virtual DOM).
2. **Переиспользование:** Возможность создавать переиспользуемые UI-компоненты.
3. **Сообщество:** Наличие большого количества готовых решений и документации.

### Рассмотренные варианты
* React
* Vue.js
* Angular

### Итог решения
Выбранный вариант: **«React»**, потому что он обеспечивает высокую скорость работы, имеет огромное сообщество и позволяет легко разбивать интерфейс на переиспользуемые компоненты.

### Последствия
* **Хорошо, потому что** SPA-приложение на React работает быстро и плавно.
* **Хорошо, потому что** компонентный подход упрощает поддержку кода.
* **Плохо, потому что** требует настройки дополнительных библиотек (например, React Router для навигации).

### Подтверждение
Проверка наличия файла `package.json` с зависимостями `react` и `react-dom`. Проверка структуры проекта на наличие папки `components/` для подтверждения компонентного подхода.

### Плюсы и минусы вариантов

#### React
* **Хорошо, потому что** огромное сообщество, высокая скорость (Virtual DOM).
* **Хорошо, потому что** легко найти готовые компоненты и библиотеки.
* **Нейтрально, потому что** требует изучения JSX-синтаксиса.
* **Плохо, потому что** требует изучения дополнительных библиотек (Router, Redux).

#### Vue.js
* **Хорошо, потому что** простой синтаксис, легкий порог входа.
* **Хорошо, потому что** встроенные механизмы реактивности.
* **Плохо, потому что** меньшее сообщество, чем у React.
* **Плохо, потому что** меньше готовых корпоративных решений.

#### Angular
* **Хорошо, потому что** полноценный фреймворк с готовыми модулями.
* **Хорошо, потому что** строгая архитектура (MVC).
* **Плохо, потому что** сложный и тяжелый для небольших проектов.
* **Плохо, потому что** требует изучения TypeScript и RxJS.

### Дополнительная информация
Решение принято с учетом популярности React на рынке и наличия большого количества готовых UI-библиотек (например, Material UI). Связанные требования из SRS: REQ-INT-001, REQ-INT-002.
